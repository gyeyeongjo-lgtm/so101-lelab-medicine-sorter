# 2026-10-08 빈 작업대 소폭 수동 이동 사전 점검

## 목적과 제한

사용자는 이동시험 가능 의사를 밝히고 빈 그리퍼·작업 범위의 물체 제거·사람 이탈·즉시 중단 준비를 확인했다. 이것은 기존 LeLab 8000 텔레옵을 사용자가 직접 조작하는 한 번의 **공중 소폭 이동** 범위다. 자동 관절 재생, World→Base/TCP 승인, URDF 상한 변경 또는 약통 집기는 포함하지 않는다. 사용자가 바구니 세 개를 치웠다는 두 번째 보고 뒤 신선한 정면·사선 화면에서 실제 빈 작업대를 확인했다.

URDF는 로봇 링크 구조와 관절 범위를 정의하는 모델이다. 장치의 raw 위치 제한과 캘리브레이션 파일은 일치하지만 설치 드라이버의 `MotorNormMode.DEGREES` 변환식 및 4095 step 해상도로 환산하면 Elbow 장치 상한은 약 +97.011°, Wrist_Pitch는 약 +100.615°인 반면 설치 URDF 상한은 +90°/+95°다. 앞선 수동 A/B/C 기록의 각 최대 +96.659°/+100.264°는 장치 상한과 약 0.352° 차이에 불과하다. 이 비교는 파일·레지스터·방송값의 수치 비교이지 실제 하드스톱 또는 충돌 없는 작동 범위의 검증이 아니다. 캘리브레이션 최대를 그대로 자동 경로 목표로 채택하지 않는다.

## 카메라 첫 실패와 관찰 경로

Mac 8030은 약 16분 전 프레임에 머물렀고 8031은 `ok=false`였다. 8000 정면 8은 HTTP 200이지만 사선 4·손목 6은 HTTP 503이었다. Jetson 실제 `/dev/video4`·`/dev/video6`은 기존 8022 LeLab 프로세스가 점유하고 있었고 그 서비스의 두 프리뷰는 HTTP 200이었다. 두 서비스 모두 텔레옵은 사전 inactive였다. 점유 프로세스를 종료하거나 USB·카메라 설정을 바꾸지 않았다.

읽기 전용 `teach_capture_web.py`에 사선/손목별 대체 프리뷰 URL 인자를 추가해 8030의 정면은 8000, 사선/손목은 8022에서 수신하도록 했다. 기존 PID·실행 명령을 확인하고 해당 Mac 8030 프로세스만 TERM 종료·재시작했다. 8030 세 영상은 처음에 수십 ms로 신선해졌고 8031도 `ok=true`·ID0–6·약통 검출 0으로 회복됐다. 그러나 8022 MJPEG 응답이 짧게 닫혀 사선/손목은 수 초씩 오래된 프레임을 간헐적으로 반환했다. 실제 프레임을 받은 스트림이 닫힐 때만 재연결 대기를 2초에서 0.1초로 줄인 뒤 10초 표본에서 사선 프레임 나이는 최대 약 807 ms로 개선됐지만 750 ms 기준을 항상 충족하지 못했다. 관찰 UI의 `robot_control=false`, 8031의 `robot_enabled=false`는 유지된다. 이 영상에 연속 안전 관찰 보증을 부여하지 않는다.

## 사용자 직접 이동 시도와 결과

사용자가 리더·팔로워 시작 자세를 맞추고 8000 텔레옵을 직접 켰으며 시작 직후 이상 움직임이 없다고 보고했다. API `teleoperation_active=true`, Mac 관절 방송은 신선했다. 첫 읽기 전용 관절 스냅샷은 Rotation +0.071348, Pitch −1.710039, Elbow +1.677818, Wrist_Pitch +0.863075, Wrist_Roll −0.258539, Jaw +0.036317 rad였다. Elbow는 URDF 상한 +1.5708 rad보다 이미 약 0.1070 rad 높았다.

에이전트는 팔꿈치만 장치 상한에서 멀어지는 방향으로 소폭 움직이고 손끝의 공중 이동을 약 1 cm 이내로 제한하도록 요청했다. 뒤이은 읽기 전용 스냅샷은 Rotation −0.1082, Pitch −1.7039, Elbow +1.6855, Wrist_Pitch +0.7618, Wrist_Roll −0.2570, Jaw +0.0363 rad였다. 따라서 두 스냅샷의 Elbow는 오히려 장치 상한 쪽으로 약 +0.0077 rad, Rotation은 약 −0.1795 rad, Wrist_Pitch는 약 −0.1013 rad 바뀌었다. 이 값은 연속 경로가 아닌 두 순간의 방송값이다. 사용자는 작은 이동 후 정지했고 접촉·이상 움직임이 없다고 보고했다. 수치가 의도한 한 관절 시험과 달라 추가 이동 중단·텔레옵 종료를 요청했다. 종료 뒤 API의 teleoperation/recording/inference active=false를 확인했다.

별도 60초 읽기 전용 관찰기는 이동 전 정지 구간에서 `max_duration`으로 끝났다. Git 제외 `.local/teleop-traces/20261007T152848_303822Z_d61edad9/`의 관절 1,156개는 모두 같은 초기 자세이며 정면 245·사선 170장의 JPEG/인덱스와 관절 파일 SHA-256 검사는 통과했다. 이 파일을 이동 연속 경로 증거로 해석하지 않는다. 이는 관찰 시작/사용자 동작 타이밍 조율 실패다. 원본은 수정·삭제하지 않았고 `use_for_replay=false`, `robot_enabled=false`, `motion_authorized=false`다.

## 판정과 후속 조건

사용자의 현장 무접촉 보고는 보존하지만 독립적인 물리 간격/속도나 한 관절 이동은 검증되지 않았다. 장치 상한 근처 자세와 관찰기 타이밍·사선 스트림 끊김이 있으므로 이번 결과로 URDF 범위를 넓히거나 자동 이동을 시작하지 않는다. 다음 실제 이동은 신뢰할 수 있는 관찰 경로와 현재 자세·조작 축을 먼저 고정한 별도 한 변수 시험으로 설계해야 한다. 로봇 직접 명령·토크 변경·설정 변경·자동 투입 `NOT_RUN`; 이슈 API 갱신 `NOT_RUN`, 원격 push `NOT_PUSHED`.
